# DLNA 模块 · 开发方向存档

> 状态：**未开工**，仅方向存档。最后更新 2026-11-04。
> 结论先行：手机发起 → PocketNAS-PC 接住 → PC 侧播放器读取。电视不在这条链路上。
> 开工前必须先回答第 7 节的四个问题，尤其是第 1 条（手机到底走不走 DLNA）。

---

## 1. 需求（按用户原话收敛）

- **发起方是手机**，不是 PC
- 第一要求：投给电视；第二要求：投给 PC
- 交互要方便：手机上点投送，PC 就开始播
- **大文件不能等全下完**（必须边收边播）
- 习惯把这类能力做成"服务"（常驻、开机自启、不依赖前台窗口）

注意第 1 条和第 2 条性质不同：**投电视的落点在手机 App（DMC 控制器），投 PC 才是本仓库要写的东西。**
如果手机 App 现在还不能投电视，真正该写代码的是 App 端，PC 端做出来也没人敲它的门。

---

## 2. 关键事实（决定方案边界，不要再推翻）

### 2.1 DLNA 投屏 = "给你个链接，你自己去下"

```
1. 手机 → PC（或电视）：SetAVTransportURI   CurrentURI = http://x.x.x.x:port/a.mp4
2. 手机 → PC：Play
3. PC 自己去 HTTP GET 那个 URL，边下边播
```

**字节不经过手机**。渲染器是主动拉流方，手机只负责告诉它去哪里拉。投完之后手机可以锁屏、退出投屏界面，播放不中断。

由此推出三条前提：

1. 那个 URL 必须渲染器能访问到（给 `127.0.0.1` 或带会话 token 的临时链接就会黑屏转圈）
2. 手机端得能提供 HTTP 服务把文件暴露出来
3. metadata（DIDL-Lite）各 App 写得五花八门，接收端要能容忍残缺，靠 URL 后缀猜类型也行

### 2.2 协议不分"发送/接收"，靠角色分工

| 角色 | 干什么 | Windows 10 |
|---|---|---|
| **DMS** 媒体服务器 | 共享内容出去 | ✅「媒体流选项」开启后即是 |
| **DMR** 渲染器 | 接收投送、播放 | ⚠️ 只有 WMP 那个半残实现 |
| **DMC** 控制器 | 发现设备、发指令（遥控器） | ✅ 资源管理器「Cast To」 |
| **DMP** 播放器 | 自己找片源播 | ❌ 已从 Win10 移除 |

底层是同一套：SSDP（发现）+ HTTP/XML（描述）+ SOAP（指令）+ HTTP GET（传流，支持 Range 所以能拖进度）。

### 2.3 服务进程里播不了画面

Windows 自 Vista 起会话隔离：服务运行在 Session 0，**没有显示器、没有桌面、没有音频设备**。

| 能服务化 | 不能服务化 |
|---|---|
| SSDP 广播、响应 M-SEARCH | 显示播放窗口 |
| 接收 SOAP 指令 | 播放视频、出声 |
| 缓存文件、写日志、开机自启 | 托盘图标、任何用户可见元素 |

WebDAV 和 sshd 能纯服务化，是因为它们不产出 UI。DLNA 接收的最终产物就是"屏幕上出现画面"，必然发生在用户会话里。
（勾"允许服务与桌面交互"从 Vista 之后失效，不要考虑。）

**结论**：主程序内跑一个后台 Host（照 WebDAV 的 Generic Host 写法），加托盘常驻实现"关窗口不退出"，对外表现接近服务。真需要多进程时再拆，把协议栈抽成独立类库即可。

## 3. 已否决的路线（不要回头重走）

| 路线 | 否决原因 |
|---|---|
| **A. 系统媒体流**（WMPNetworkSvc） | 只能做 **DMS 发送**，做不了接收；且只认 Windows 媒体库（要"塞库"污染资源管理器）、依赖 WMP 可选功能 |
| **B. 内嵌 MiniDLNA** | 同样是发送方；GPLv2；无官方 Windows 二进制 |
| 自研完整 DMS | 需求方向反了 |
| **Miracast**（无线显示器） | 若手机走的是整屏镜像，与 DLNA 无关，用 Windows 自带功能即可，不写代码 |
| **AirPlay** | 另一套协议，明确不支持 |
| 音量控制（RenderingControl） | **过度设计**。PC 用系统音量，手机调音量不该经过投屏协议 |
| GENA 事件订阅 / 状态回报 | **过度设计**。只是为了让手机 UI 显示进度条，不做只表现为"位置未知"，不影响播放 |
| 转码、字幕外挂、多设备队列 | 与"投送即播"需求无关 |

**保留**：Play / Pause / Stop / Seek 四个核心控制。少了这些用起来别扭。

## 4. 目标链路

```
手机 ──► PocketNAS-PC（接住） ──► 播放器读取
                                    └─ VLC / libVLC
```

电视**不走这条链路**（手机可以直接投电视，与本仓库无关）。

"接住"有两种深度，工作量差一个数量级，**待定**：

| | 直连 | 中转 |
|---|---|---|
| 链路 | 手机给 PC 一个可访问 URL → `vlc <url>` | 手机推字节 → PC 中转 → `vlc http://127.0.0.1:port/stream/x` |
| 秒开 | ✅ VLC 首字节就出画 | ✅ 前提是"边收边吐" |
| 代码量 | 几十行（起进程 + 记一条记录） | 多几百行（接收 + 分块 + 阻塞读 + 清理） |
| 前提 | 手机 App 能提供可访问的 HTTP 地址 | 无所谓，手机推什么都行 |

**VLC 本身天生流式**：`vlc http://...4GB.mp4` 两秒内出画面，后面的字节边播边下。所以"大文件不能等全下完"这条**直连就能满足**，不构成做中转的理由。真正需要中转的是下面两种情况。

### 4.1 必须中转的两种情况

1. **PC 拉不到手机给的地址**（手机连热点、PC 连有线、跨网段）
2. **源带时效鉴权**。已实测的链接形如：

   ```
   https://192.168.3.220:8443/dav/下载/xxx.mp4?k=1793839785-93fe06682a377cbb46c7
   ```

   `k` 疑似签名 + 时间戳。短片段无所谓；**长片播到一半签名过期、拖进度会 403**。
   一旦实测确认这点，"中转 + 落盘缓存"就从可选变成必需——PC 先把流接住存本地，播放器只读本地文件。

### 4.2 中转若要做，"边收边吐"有两种

- **纯管道（不落盘）**：简单、不占磁盘；但拖动依赖上游支持 Range，否则一拖就得从头拉
- **落盘缓存 + 阻塞读**：拖动完全本地化、可重复播放、手机断开也能播完已缓存部分；代价是要处理读写同步、边界等待、临时文件清理，是整条链路最容易出 bug 的地方

投屏场景用户一定会拖进度条，**优先选落盘缓存**。

## 5. 手机 → PC 的交互通道，建议不用 DLNA

手机端做 SSDP 发现（UDP 组播）很容易踩 Android 的组播权限、多网卡、AP 隔离这些坑，收益不过是"看起来像标准投屏"。
既然 App 是我们自己的，用一个简单 HTTP 接口更可靠：

```
POST http://<pc>:9528/cast
{ "url": "https://.../movie.mp4", "title": "...", "target": "local" }
```

PC 收到后校验并起播放器。手机端一个 `HttpClient.PostAsync` 就完事。

备选：注册自定义协议 `pocketnas://cast?u=...`，手机上点链接或扫码即唤起，适合"从浏览器/聊天里直接投"。

### 安全底线（这个端点等于"谁都能让你电脑弹窗播视频"）

- 只监听局域网网卡，不开公网
- URL 里带 `?token=xxx` 共享密钥
- 或首次配对确认一次，之后记住

## 6. 参考项目

| 项目 | 语言 / 许可 | 价值 |
|---|---|---|
| **Macast**（gitee.com/xfangfang/Macast） | Python，GPL-3.0 | **最贴近目标**：托盘常驻、手机投电脑、外部 mpv + JSON IPC、插件机制适配国内 App 魔改协议、`http://IP:1068` 自检排障路径 |
| gmrender-resurrect | C + GStreamer + libupnp，GPL | 最干净的 DMR 参考，几千行 |
| Platinum UPnP SDK | C++，带 VS 工程 | 有完整 MediaRenderer 示例，Windows 可直接跑对照 |
| libupnp 的 `tv_device` | C | 最小 DMR 样例 |
| Coherence | Python | MediaRenderer 状态机写得最清楚 |

均为 GPL 系，**只读思路，不拷代码**。设备描述 XML、SSDP 响应字段属协议规范，可照抄。

**.NET 现实**：没有成熟 DMR 库。`Rssdp`（MIT）只能解决 SSDP 发现这一小半。

**Macast 给的两个警钟**：
1. 它有 `nirvana` 这类插件专做**国内 App 私有魔改的 DLNA 协议**——说明只实现标准协议，未必连得上 B 站、爱奇艺、优酷。第一版能做到"标准 DLNA App / 系统相册能投"就算成功。
2. 播放走外部 mpv + IPC，控制能力（实时状态、精确 seek、切轨）比内嵌播放器完整，且播放器崩了不拖累主程序。

## 7. 若确认要走标准 DMR（手机只认 DLNA 投送）

仅当第 8 节问题 1 的答案是"DLNA"时才需要这一节。

**协议层**（砍掉 GENA 与音量后约 **800~1200 行**）：

```
SSDP     NOTIFY alive/byebye + 响应 M-SEARCH        ~200 行
HTTP     /description.xml + 两个服务的 SCPD          ~150 行
SOAP     AVTransport（SetAVTransportURI/Play/Pause/Stop/Seek）  ~400 行
播放集成  收到 URI → 拉流 → 回报 TransportState        ~300 行
```

**播放内核**：**LibVLCSharp**（`VideoLAN.LibVLC.Windows`，LGPL-2.1，可闭源商用）。

选择理由：DMR 的播放窗口很朴素（一个视频 + 控制条），不需要复杂叠加，airspace 影响小；而**"什么都能播"对投屏最关键**——手机投过来的格式不可控，一旦播不了，用户第一反应是"这功能不行"。FlyleafLib 的优势在"把播放器做精致"，那是本机播放器的需求。

坑：`VideoView` 内部是 `WindowsFormsHost`，WPF 控件无法叠加在视频上，**控制条不能浮在画面里**；高 DPI 下要设缩放模式，否则糊。

**实施顺序**（每阶段一个 commit，可独立验收）：

| 阶段 | 目标 | 验收 |
|---|---|---|
| D1 | 空壳 DMR，能被发现 | 手机投屏列表出现「PocketNAS-PC」 |
| D2 | 能播放：收 URI + Play | 手机点投送，PC 出画面 |
| D3 | 基础控制：Pause / Stop / Seek | 手机上按暂停，PC 跟着停 |
| D4 | 兼容性：BubbleUPnP、各视频 App、系统投屏 | 逐个真机过一遍 |

**D1 是分水岭**：能看到设备，后面都是可控的工程问题；看不到，说明手机根本不用 DLNA，白做。

## 8. 与 FTPS 模块的关系（可能让 DLNA 大幅缩水）

FTPS 模块已实现（21 显式 / 990 隐式，VLC 走 990）。如果手机侧能经 FTPS 提供文件、PC 用 VLC 拉 `ftps://`，那 DLNA 模块可以退化为"**接住一个 URL 并起播放器**"，协议层工作量大半消失。

需要单独评估的点：FTP 每次 seek 都要重建数据连接 + `REST`，不如 HTTP Range 顺；但现有实现已为 VLC 做过 `ABOR`/`REST` 兼容（见 FtpsServer 注释），实际够不够用需要实测。

## 9. 开工前必须回答

| # | 问题 | 影响 |
|---|---|---|
| **1** | 手机点「投屏」时，弹出的是**设备列表**还是直接进入**镜像中**？ | 决定这条路线是否成立。若是 Miracast，本模块不用写 |
| **2** | 手机 App 能否给出一个 **PC 可直接访问的 URL**？ | 决定直连（几十行）还是中转（几百行） |
| **3** | 那个 `?k=` 签名链接，**拖进度会不会 403**？ | 决定要不要落盘缓存 |
| **4** | 投屏时 PC 的界面形态：独立窗口 / 内嵌主界面 / 全屏？主界面要不要让位？ | UI 方案 |
| 5 | 局域网任何人都能投，要不要首次弹确认？ | 安全与体验 |
| 6 | 模块叫「DLNA」还是「投屏接收」？ | 实际只做接收，叫 DLNA 会让人以为也能共享文件出去 |

问题 1 的判断方法（30 秒）：手机打开要投的视频点「投屏」——

- 出现设备名（电视、机顶盒）且可选中 → **DLNA**
- 提示「正在连接 / 正在镜像」，手机画面整体出现 → **Miracast**，本模块作废

## 10. 其他结论

- **不自己实现 UPnP AV 协议栈**这句话已作废：如果确认走 DMR，协议栈必须自己写（.NET 无可用库）。但范围收窄到 AVTransport 一个服务，不碰 RenderingControl / ConnectionManager 的完整实现。
- Win10 已于 2025-10-14 停止支持，相关系统组件仍可用但不再更新
- 播放期间电脑不能休眠；访客 Wi-Fi 会隔离设备，必然发现不到
- 排障顺序（抄自 Macast）：自检端口能否打开 → 防火墙 → 路由器 UPnP/AP 隔离 → App 本地网络权限 → 是否同网段
